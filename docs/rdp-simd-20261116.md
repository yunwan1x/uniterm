# Browser RDP SIMD experiment — held from production

The candidate is **not released**. In the real 1080p scrolling test it improved
display submission rate by 10.41%, but the complete video comparison did not
establish a benefit and showed a repeatable association with more dropped frames
reported by the Win11 source. All four SIMD rounds had a larger source drop
increment than all four scalar rounds. That is a reason to hold the change, not
proof that SIMD caused the drops.

Production remains rc.8 (`65a5f700` code). Candidate source is retained separately
at `d18e2769826eded3dfefb8c2bb5289a83e65c57b` on
`experiment/rdp-simd-release-20261115`. No candidate production server was built
or installed, and the candidate source was not merged into main.

The remaining CPU path performs AVC444 YUV-to-RGBA conversion before the
Canvas2D compositor presents a remote picture. `uniterm.18` compiles the same
portable Rust source with ordinary release settings and with
`-C target-feature=+simd128`. It does not change the conversion formulas, the
graphics protocol, the presentation queue or the TypeScript application.

The original scalar `uniterm.17` WASM is retained byte-for-byte. A small
`WebAssembly.validate` probe selects one binary before fetching it, in both the
Worker and main-thread fallback. Explicit initializer inputs and `initSync`
retain their original behavior. Initialization errors propagate to the caller.
The runtime package has no new dependencies.

## Source and package verification

Both engines use IronRDP base `905c28b3a4e67b15fac274c5d808ef3cef0eb813`, the
complete existing 25-file patch (SHA256
`a4c3e3f9a0f78226ccbd16f33a1b1d962dccf016110f830e32485f9e39ca5fe5`),
Rust 1.99.1 and wasm-bindgen 0.2.129. The original dirty checkout and the existing
GPU-copy checkout were not modified. The new build's source, patch and index
hashes were checked before and after compilation.

The build-only packager validates the scalar binary with SIMD disabled and the
candidate with standard SIMD enabled. It rejects relaxed SIMD, invalid binaries,
ABI differences, changed snippets or declaration files, and executable binding
differences. Acorn restricts the sole allowed binding difference to generated
`shim_idx` decimal values inside actual comments. WABT validates complete
modules; this is not a search for opcode-like bytes.

The loader, ABI guard and packager tests pass 27/27. The release build script's
isolated command-flow checks pass 13/13, including empty encoded Rust flags,
failed Git status, dirty checkout, stale output, linked worktree and production
NODE_ENV. These mocked checks do not substitute for the real WASM and Vite builds.

Disassembly confirms 162 SIMD instructions in the full production candidate's
`Yuv444Frame::to_rgba`. The global compiler flag also affects other engine code,
so converter measurements alone cannot establish compatibility or end-to-end gain.

## Converter correctness and performance

Separate scalar and SIMD modules were compared byte-for-byte over 94,032 checks,
1,798,149,888 output bytes, 102 fixtures and 204 incremental states. An independent
JavaScript oracle checked 1,747,836 pixels. Coverage includes both AVC444 layouts,
odd offsets and tails, thresholds 29/30/31, clamping, clipped/empty crops, separate
main/aux updates and 1080p/4K frames. Input planes remained unchanged. Native
baseline tests also passed; those native tests do not exercise WASM SIMD.

The NAS Chromium 156 benchmark runs in a Worker with independently warmed
implementations and alternating ABBA/BAAB blocks. There are 32 blocks per engine.
The two automatic-vectorization captures show:

| Capture / full frame | Scalar | SIMD | Time reduction |
| --- | ---: | ---: | ---: |
| First, 1920x1080 | 6.567 ms | 3.467 ms | 47.2% |
| Repeat, 1920x1080 | 6.667 ms | 3.533 ms | 47.0% |
| First, 3840x2160 | 26.6 ms | 13.9 ms | 47.7% |
| Repeat, 3840x2160 | 26.8 ms | 13.8 ms | 48.5% |

These are medians of per-block iteration averages, including Rust allocation and
excluding JavaScript copies and comparison. They are not individual-frame latency
percentiles, decoder FPS or physical display FPS. Small width-three tails were
effectively tied at the browser timer resolution. A hand-written SIMD experiment
also passed correctness but was not selected: automatic vectorization performed
slightly better on large cases while retaining the portable source unchanged.

## Browser compatibility

The real NAS browser initialized the package in both main and Worker realms,
once with its native SIMD probe and once with only that probe forced false. All
four cases fetched exactly one WASM, matched its complete expected SHA256 and
exposed the expected API. This checks the scalar selection path on a current
engine; it is not a test of every older browser or physical GPU.

A real RDP session through the Vite bundle with the probe forced false remains
**unverified**. The first two injection controllers failed before recording the
actual selected engine, and their error collection was insufficient. Review
found Node/browser HTTPS handling differences and an unauthenticated download
that returned login HTML. The final functional retry used the authenticated
JavaScript response (59,701 bytes, SHA256
`ee078c7a9e2e09b8e0e35f9fbed5efa98c543f0066aaea36bef7e88c1e3388c4`)
and retained its failure evidence. Chromium blocked the injected Worker response
with `net::ERR_BLOCKED_BY_RESPONSE`, before probe execution or WASM initialization.
The controller omitted original response security-policy headers. These attempts
do not establish an application scalar fallback failure, but they also do not
verify a complete bundled scalar RDP connection. This limitation is retained;
the passing raw-package initialization tests must not be described as that check.

## Live comparison

An isolated NAS Chromium client connects to the real Win11 host at actual
1920x1080. The two servers use identical diagnostic JavaScript, flow tracing off,
presentation tracing on, region budget one and one presentation slot. Each
workload runs A-B-B-A for 30 seconds per round, without profiling or compilation.
Each round verifies the selected runtime WASM and complete hash outside the
measurement window. The extra hash fetch is separate from the Worker loader.

The completed scrolling comparison has 4,304 complete display batches. An
independent analyzer recomputed the raw events without importing the capture
metrics implementation. Source scroll requests stayed at 31.973–32.025/s,
viewport 1872x1057/DPR 1 and content height were identical, video was paused,
and no animated Canvas source was active.

| Scroll round | Submissions/s | Gap P95 | Gap P99 | Maximum | >100 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| A1, scalar | 34.196 | 59.840 ms | 69.465 ms | 81.890 ms | 0 |
| B1, SIMD | 37.548 | 47.875 ms | 59.480 ms | 64.325 ms | 0 |
| B2, SIMD | 37.584 | 47.530 ms | 57.155 ms | 86.425 ms | 0 |
| A2, scalar | 33.852 | 58.550 ms | 75.120 ms | 85.400 ms | 0 |

Across scrolling rounds, submissions increased from 34.024/s to 37.566/s
(+10.41%). Pooled gap P95 fell from 59.515 to 47.665 ms and P99 from 70.515 to
58.075 ms. Both candidate rounds improved those percentiles relative to both
baseline rounds. The single maximum gap did not improve (85.400 to 86.425 ms).
These are JavaScript display submissions, not distinct source frames or physical
monitor FPS; partial/desktop updates can make submissions exceed source requests.

The first video ABBA sequence was valid but did not establish a benefit:
submission rate was 32.086/s on scalar and 32.107/s on SIMD (+0.066%, effectively
unchanged). Pooled P99 worsened from 80.060 to 87.330 ms; gaps above 100 ms were
8 versus 13. Both SIMD rounds had more such gaps (7/6) than either scalar round
(5/3). Source dropped-frame increments also varied (3/17/15/11 in chronological
order), so these observations cannot by themselves assign the difference to SIMD.
They are retained as an explicit concern, not described as a regression-free run.

The additional reverse-order BAAB sequence was specified before its execution
and kept alongside the first sequence. It improved pooled P99 (78.385 to
73.900 ms), so the first sequence's P99 worsening did not repeat. However,
source dropped-frame increments remained separated by implementation.

| Video round order | Engine | Submissions/s | Gap P99 | >100 ms | Source dropped increment |
| --- | --- | ---: | ---: | ---: | ---: |
| First A1 | Scalar | 31.898 | 75.350 ms | 5 | 3 |
| First B1 | SIMD | 32.440 | 87.240 ms | 7 | 17 |
| First B2 | SIMD | 31.775 | 89.680 ms | 6 | 15 |
| First A2 | Scalar | 32.275 | 83.565 ms | 3 | 11 |
| Reverse B3 | SIMD | 32.142 | 75.555 ms | 5 | 28 |
| Reverse A3 | Scalar | 32.021 | 78.385 ms | 3 | 13 |
| Reverse A4 | Scalar | 32.166 | 78.960 ms | 3 | 4 |
| Reverse B4 | SIMD | 32.900 | 73.900 ms | 2 | 23 |

Across all eight video rounds, submissions changed from 32.090/s to 32.314/s
(+0.70%), pooled P99 from 78.965 to 82.115 ms (+3.99%), and gaps above 100 ms
from 14 to 20. Edge's source quality counters recorded 31 dropped out of 3,161
total frames for scalar (0.981%) and 83 out of 3,163 for SIMD (2.624%). The
source clip, source configuration, viewport and page time origin were unchanged.
Every round had 12 media-time wraps and 12 recurring source callback gaps over
200 ms; unequal loop counts do not explain the result. Callback counts are not
physical presentation counts, and the file's timestamp structure was not examined.

All 12 scrolling/video runs passed trace integrity checks; independent
recomputation found zero metric mismatches. All data, including the concerning
first video group, are preserved in the frozen comparison snapshot.

Review of the first group's 21 gaps above 100 ms found that the final
ready-to-draw stage averaged about 0.9–1.0 ms. The larger interval occurred before
the next recorded decode start/damage. Those earlier captures did not trace all
network, conversion and scheduling stages, so their blank intervals cannot be
called CPU idle time or network wait, and do not clear the regression concern.

## Separate stall diagnostics

Diagnostic JavaScript and Rust hooks are excluded from production and from the
release WASM performance comparison. The instrumented scalar engine has SHA256
`58ec511178cd0e223ecb8118a273bce4e5b679f5430eb8c961d1e61bdb8b0a04`.
Trace events contain stage names, numeric timing/identity/queue information,
without payloads, credentials or screen content. Tracing is opt-in and off by
default; its timing is not pooled into release A/B results.
The diagnostic application is preserved on its isolated branch at
`cf335aa04b3a7a82801e18beaee3964c851a371b`, with the complete diagnostic Rust
patch retained separately (SHA256
`c1be515edb8c0988ae93349a59c7ea9123ccddf64de96e42dec80af51c4c6800`).

The first capture reached the 65,536-event main buffer and reported 36,968
dropped events. Its original Worker limit was 4,096 per drain and did not report
drop sources separately. It is retained as **invalid for stall attribution**.
Only the isolated diagnostic application was changed to bounded capacities of
16,384 Worker events and 262,144 main events, adding separate drop/peak counters.
The relevant three test suites / 14 tests and strict targeted TypeScript check
passed before one repeat; there was no repeated search for a favorable sample.

The repeated 15-second phase retained 99,509 events across 19 contiguous drains.
Worker/main drop counts were both zero, Worker peak drain was 6,226, and main
retained peak was 99,509. Independent review confirmed stable diagnostic WASM,
complete in-phase ordered display chains and paired spans, with boundary-only
unpaired records reported separately. There were 492 complete draw submissions.
The maximum gap was 99.715 ms and no gap exceeded 100 ms. This does not reproduce
or explain the earlier longer stalls and does not prove they are eliminated.

Selected stage measurements from this separate instrumented phase:

| Stage | P95 wall time | Maximum wall time |
| --- | ---: | ---: |
| Pending-graphics processing call | 13.090 ms | 30.560 ms |
| Decode request to observed ready continuation | 18.210 ms | 30.505 ms |
| Snapshot start to ready | 6.985 ms | 15.955 ms |
| Main receive to draw start | 16.925 ms | 22.540 ms |
| Main draw submission call | 0.100 ms | 0.735 ms |

These observations identify work and scheduling intervals to investigate. They
are not independent CPU costs: stages may overlap, command counts differ, and
async completion timestamps include scheduling. Summing their percentiles would
not yield a frame's latency. No physical monitor presentation was measured.

The corresponding Win11 counter capture contains 30 samples for `rdp-tcp 0`.
Using both clock uncertainty (approximately ±216.1 ms after combination) and
each counter's preceding sampling interval, 14 full intervals fit conservatively
inside the diagnostic phase. Input and output rates were equal in every one,
ranging from 21.870 to 31.638/s; average encoding time ranged from 13 to 27 ms.
All three reported RDP skip categories were zero in those intervals. One network
skip sample elsewhere in the file preceded this phase and is not included.
These one-second counters provide context, not per-gap attribution or an A/B
comparison. `Source Frames/Second=0` is not evidence of a frozen source: Microsoft
documents that counter as unsupported. Edge's own video quality counter is a
separate measurement. See [RemoteFX counter documentation](https://learn.microsoft.com/en-us/azure/virtual-desktop/remotefx-graphics-performance-counters).

## Protocol feedback review

Source inspection confirms that color conversion runs in FIFO graphics work
before EndFrame creates the protocol FrameAcknowledge. The response then passes
through an independent outgoing writer. Canvas rendering and the subsequent
main/Worker display acknowledgement are a separate path: the RDP protocol ACK
does not wait for that local display handshake. Faster synchronous processing
can therefore change scheduling or response timing, but the current generic
`response-enqueued` trace does not identify an ACK or establish server receipt.

The current `queueDepth=Unavailable` is consistent with the normal path in
FreeRDP commit `11bfdcf8453dcb63ce5e702cd9f71830f94a9efc`. The Microsoft field is
defined in buffered bytes, not frames; the local scheduler's estimated memory
usage is not automatically a valid value for it. No ACK policy was changed.
See [Microsoft ACK format](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpegfx/0241e258-77ef-4a58-b426-5039ed6296ce),
[EndFrame handling](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpegfx/b140c496-b743-4548-84d9-f3c0b151f374),
[server ACK handling](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpegfx/d64cfae6-f30a-47e7-9655-d019d3d8fb0f)
and [fixed FreeRDP source](https://github.com/FreeRDP/FreeRDP/blob/11bfdcf8453dcb63ce5e702cd9f71830f94a9efc/channels/rdpgfx/client/rdpgfx_main.c#L1550).

This is a plausible feedback path to measure, not a demonstrated cause of the
source drops. No artificial ACK delay, frame interpolation or speculative
protocol change is justified by the current evidence.

## Release decision and evidence

The SIMD change remains experimental. A faster converter and better scrolling
do not establish an improvement to the user's video workload. The unchanged
production rc.8 archive remains available; there was no deployment to roll back.

Preparation included an installation helper with 20 passing local failure and
control-flow tests and a production-build guard with eight passing local tests.
Neither the production build helper nor the installer was executed on the live
service. These tests validate preparation only and are not evidence of deployment.

Owned Windows source/task/profile, NAS test browser, diagnostic services and
relays were stopped; their ports and process identities were checked. Derived
gateway credentials, TLS material and temporary fixture/build directories were
removed. User processes and the production router service were left running.
Candidate/diagnostic source worktrees and review evidence are retained.

The final router health endpoint returned `status=ok`. Server SHA256 remains
`27991dbd0033d59adf445ce7f40e24c19db616f2d27995af71f17a38bc76ce45` and
gateway SHA256 remains
`22d3c4d6c805d92661f9b2b1ac7945e9e28f0478174f74928d324a4684c596a5`.
Before this documentation update, main was clean at
`999549700b2cfbefa1323aa747cbdef3f26efb40`; only this report is added to main.

Evidence is preserved as `rdp-simd-evidence-20261116.tar.gz` in
`/vol1/1000/wy/uniterm-rdp-evidence/`, with an external per-file manifest and
archive verification JSON. The archive contains the nine `uniterm-simd-*` trees:
bench, opt, review, release, live, diagnostics, analysis, flow-review and
feedback-review. It includes source patches, raw measurements, the invalid first
flow, the valid repeat, failed compatibility controllers, independent analyzers,
checks and cleanup records. Dependency caches and private unlock input are
excluded; the supplied credential value is scanned before the private input is
deleted. Every archived regular file is checked against its recorded SHA256.

The most useful next diagnostic would identify real protocol ACK creation and
writer operations by numeric frame/token identity without changing their timing
policy. Existing generic response events cannot answer that question. It has
not been implemented in this round; no new causal conclusion or release approval
is implied by this proposed measurement.
