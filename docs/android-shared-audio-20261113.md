# Android / RDP 共用 PCM 播放器验收（2026-11-13）

Android 改为使用 `frontend/src/utils/pcmAudio.ts`。RDP 保留原 API 名称，通过重导出使用同一实现。

## 行为

- 连续时间轴排队，初始预缓冲 120ms，目标缓冲按抖动调整在 80–150ms 范围。
- 积压超过 500ms 时保留正在播放的片段并裁剪未来积压；不会像原 Android 实现那样超过 250ms 就丢弃新包。
- 每个会话独立播放器；手势启用、挂起清理、恢复和断线释放；音频错误不打断视频。
- Android 仍使用 scrcpy raw PCM（48kHz / 双声道 / 16bit），此次未更改压缩编码。

## 自动测试与构建

27 项测试通过，覆盖 PCM 解码、连续调度、积压裁剪、RDP 别名一致性、Android 手势启用、挂起、会话隔离、断线清理及异常帧。前端生产构建、Go server/gateway 构建及 git diff --check 通过。
全量 vue-tsc 仍有既存的 570 项错误，本次修改文件无报错；不能视为全项目类型检查通过。

## 实际浏览器验收

本机 redroid Android 12 → scrcpy → Go ADB / uniTerm → Chromium。播放 45 秒测试视频，音轨为左 440Hz / 右 880Hz。通过测试专用 AudioWorklet 在音频线程采集播放器合成输出，避免主线程录音器自身丢帧。每个场景测量约 6 秒。

| 场景 | 输出长度 | ≥2ms 静音断裂（左右） | 欠载 / 溢出 / 丢弃 |
|---|---:|---:|---|
| 正常播放 | 5.973s | 0 / 0 | 0 / 0 / 0ms |
| 每 13 个音频包延迟 80ms，保持音频顺序 | 5.973s | 0 / 0 | 0 / 0 / 0ms |
| 每 500ms 阻塞浏览器主线程 60ms | 6.059s | 0 / 0 | 0 / 0 / 0ms |

左右声道主频约 440Hz / 880Hz；非零 RMS 约 0.005016。最大实际到达间隔约 109.33ms，最大排队约 144ms。后两个场景各继续渲染 180 帧视频。停止 redroid 后 AudioContext 进入 closed，浏览器异常为 0。

## 范围与限制

这是本机 redroid + Chromium 测试，延迟注入发生在浏览器音频消息入口，不代表真实 Wi-Fi 弱网、所有实体设备或所有浏览器。超出当前缓冲的长时间阻塞仍可导致断音，不能保证任意网络条件下完全连续。没有进行本次改造前后性能百分比比较。

调试录音导出曾阻塞页面，产生额外 280ms 到达间隔及欠载；验收脚本已改为所有播放阶段结束后统一导出，以上是修正测量干扰后的结果。首次测试夹具文件未就绪及中间录音脚本错误不计为有效验收。

测试脚本、输出波形（48kHz float32 LE）、原始计数与分析结果保存在同目录。没有发布镜像或推送代码。
