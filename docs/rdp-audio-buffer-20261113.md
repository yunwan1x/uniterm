# RDP 音频连续性修复与验收

日期：2026-11-13

## 修改

- 连续片段严格沿上一片段的结束时间播放，取消逐包强制“当前时间 + 20ms”造成的空隙。
- 启动预留 120ms；按到包抖动估计，将后续启动/断粮恢复的预留调整到 80～150ms。调整估计值不移动正在健康播放的时间线。
- 队列上限提高至 500ms。超过上限时，保留正在播放或即将播放的片段，整理未来积压，保留最新音频尾部。另有节点数量限制，防止大量极小包占用资源。
- RDPSND Close 让已排队声音自然播完，并把下一段标记为新音流；暂停/断开则清理过期声音。
- 增加接收包数、字节数、缓存余量、目标预留、到包抖动、最大到包间隔、断粮次数与丢弃时长统计。调试数据位于 RDP canvas 的 data-rdp-audio-stats；不增加音量或静音按钮。

## 浏览器旧版/新版对照

运行实际 RdpAudioPlayer，输入同一组 100 个 40ms 的立体声 PCM 包：开头集中送达 8 包，后续定期插入 80ms 迟到并按序集中释放。旧代码来自当前 HEAD，修改代码来自工作区。

用 AudioWorklet 在浏览器音频线程录取实际输出；该 Worklet 仅是测试录音器，生产播放器仍使用 Web Audio 调度。分析排除启动等待和结束静音，统计幅度小于 1e-7 且持续至少 2ms 的内部静音。

|---|---:|---:|
| 检出的内部静音间隙 | 5 次 | 0 次 |

## 真实 Linux RDP 验收

隔离的 xrdp 0.10.6.1 / XFCE / PulseAudio，真实 RDPSND 通道，uniTerm 生产前端与 Go 服务。远端 paplay 播放 5 秒 440Hz 左声道、880Hz 右声道测试音。浏览器采集 AudioWorklet 位于实际播放器输出之后，不直接向播放器注入测试 PCM。

| 场景 | 输出结果 | 断粮 / 丢弃 |
|---|---|---|
| 正常传输 | 左右声道均完整约 5 秒；未检出 ≥2ms 内部静音 | 0 / 0 |
| 到包抖动 | 在 Worker→页面的音频交付入口，每 13 包延迟一组 80ms，保持顺序；8 组延迟，输出仍完整 | 0 / 0 |
| 页面忙碌 | 每 500ms 阻塞主线程 60ms；输出仍完整 | 0 / 0 |

三个场景录音主频约 440.08Hz / 880.17Hz，RMS 约 0.25894，信号持续 4.99998 秒。抖动场景观察到最大到包间隔约 179.95ms；三场景累计最大排队约 242.88ms。无浏览器 pageerror。

说明：额外抖动注入在已解码的音频交付入口，不是对整条 TCP 网络连接做限速/丢包。正常 Linux 链路是真实端到端路径。未实测 Windows、真实弱网、后台标签页节流和长时间运行；这些结果不代表所有条件下绝对不会断音。未进行人工听音验收。
