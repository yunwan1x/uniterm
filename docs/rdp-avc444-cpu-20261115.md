# AVC444 CPU conversion

Win11 RDP scrolling in the NAS Chromium Canvas2D client exposed a synchronous
color-conversion bottleneck in the session Worker. A 15-second CPU-only profile
at 1920x1080 attributed 31.1% of sampled time to `Yuv444Frame::to_rgba`.
The separate codec Worker profile does not account for native decoder threads.

In one correlated timeline interval, a snapshot timer was already queued when
decoding completed. The session Worker task lasted 16.768 ms, with consecutive
`to_rgba` sample points spanning 9.97 ms; the timer fired after 17.215 ms.
A separate decode-ready-to-snapshot interval lasted 3.730 ms and contained no
conversion samples. Its timer fired 4.096 ms after installation, closely matching
the reported 4 ms delay. The conversion does not explain every gap. The combined
profile contains negative sampling deltas and is used only for correlated event
timelines; the aggregate hotspot percentage comes from the CPU-only capture,
which has no negative deltas.

## Implementation

`0.5.1-uniterm.16` preallocates RGBA output and converts row slices. Odd rows use
a straight pixel loop. Even rows handle an odd leading column, paired pixels,
and a possible final even column separately. Paired conversion replaces repeated
per-pixel parity tests and whole-plane indexing with paired slices. Padded neighbours remain
available beyond crop and visible picture edges.

The color matrix, clamp order, reverse-filter threshold and output pixels retain
their previous behavior. This is safe scalar Rust with no additional SIMD
requirement. The JavaScript glue and both TypeScript declaration files are
byte-identical to version 15.

## Validation

The complete AVC444 test module passed 25/25 cases on both implementations.
Four added cases use fixed expected pixels for odd crop origins, odd picture
edges and independent U/V filtering around the threshold. The module ran through
an isolated manifest with all 99 registry package versions and checksums matched
against the fork's lockfile. The full core suite was interrupted before its tests
ran and is not counted as passing.

Both implementations were compiled into the same release WASM for browser
checks. All 17,550 output comparisons passed, covering 1,791,964,296 output bytes,
AVC444/V2, clipped/empty rectangles and separate main/auxiliary updates. An
independent integer oracle also checked 201,438 pixels.

| Converter-only workload | Original | Updated | Reduction |
| --- | ---: | ---: | ---: |
| 1920x1080 random chroma | 8.65 ms | 6.55 ms | 24.3% |
| 3840x2160 random chroma | 35.20 ms | 26.60 ms | 24.4% |

These are medians of batch-normalized timings from the same NAS Chromium
Worker, with alternating implementation order. The eight tested region patterns
improved by 24.3% to 28.1%. They exclude decoding, composition, network and display
scheduling and do not establish an end-to-end frame rate.

The combined patch was applied to a clean checkout of
`905c28b3a4e67b15fac274c5d808ef3cef0eb813`; converter and regression-test sources
matched the build inputs exactly. The complete web WASM, Vite bundle and isolated
Linux server builds passed.

## Live comparison

The same NAS Chromium client connected to Win11 at actual 1920x1080, using
Canvas2D and one presentation buffer. Scrolling and video each ran A-B-B-A,
30 seconds per round, with the same source page and saved video. The isolated
NAS gateway, experimental trace instrumentation and other settings were identical
between builds. CPU/timeline profiling was off during these rounds. Every round
verified the running Worker's WASM asset at its start and end.

All eight accepted rounds passed validation: 7,662 complete display batches,
no page errors and eight successful F8 input checks outside the sampling windows.
The table pools intervals within each workload/build; submission rate is the
total batch count divided by the total measured duration.

| Workload/build | Submissions/s | Gap P95 | Gap P99 | Max gap | Gaps >100 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| Scroll, original | 30.27 | 67.85 ms | 79.86 ms | 106.50 ms | 2 |
| Scroll, updated | 32.03 | 62.14 ms | 73.42 ms | 171.04 ms | 1 |
| Video, original | 32.21 | 59.57 ms | 64.98 ms | 109.89 ms | 1 |
| Video, updated | 32.94 | 57.89 ms | 65.89 ms | 108.58 ms | 2 |

Scroll submission throughput increased 5.82%, with both updated rounds improving
P95 and P99 relative to both original rounds. Video throughput increased 2.25%
and P95 decreased, but P99 did not improve consistently. Two rounds per condition
support a descriptive comparison, not a precise population effect. These are
JavaScript display submissions, not physical display frames or distinct video
frames. Source scroll updates were about 32/s; video callbacks were about 17/s.
Source callback frequency is not a frame-loss denominator.
The source video's dropped-frame counter increased by 18/7/21/6 in accepted
A1/B1/B2/A2 rounds, respectively. Its own playback was therefore not an ideal
constant-rate reference; the video results should not be generalized to all
video content or client hardware.

The updated scroll round's 171.04 ms gap includes 133.705 ms between the main
thread sending a local ACK and the Worker processing it. No already-started AVC
decode or Worker trace event spans that interval. The original run also had a
40.775 ms local ACK delay. These traces do not distinguish uninstrumented
synchronous work, GC or OS scheduling, and do not establish the cause of the
isolated maximum. Rare stalls remain.

An initial video B1 attempt was rejected because the test page's pause helper
interrupted its own asynchronous play request. Its raw file remains explicitly
marked invalid; the helper was corrected and B1/B2/A2 rerun. A service preflight
also needed SO_REUSEADDR to tolerate TIME_WAIT before scroll A2. Both repairs
occurred outside accepted measurement windows.

The shipping change contains only the converter, regression coverage and vendor
package update. It retains the production presentation mechanism. The optional
two-buffer experiment is excluded. The evidence supports shipping this bounded
CPU reduction while leaving video and occasional scheduling stalls unresolved.
The NAS gateway measurements do not substitute for production-router acceptance.

Raw captures, valid/invalid round files, benchmark sources/results and manifests
are retained in the accompanying `rdp-avc444-evidence-20261115.tar.gz` archive.
`uniterm-worker-live/rgba-abba-summary.json` identifies the accepted input files;
`uniterm-rgba-gap-analysis/findings.json` contains the selected long-gap analysis.
