# RDP 局部截图与 Worker 停顿实测（2026-11-15）

## 结论

本轮四区域截图候选没有在真实连接中触发多区域输出，不能证明有性能收益，不设为默认，也不随该实验更新路由器。测试基线为 rc.7 / AVC444 uniterm.16；随后独立进行的 GPU bridge 参数复制优化见 `rdp-gpu-copy-20261115.md`。

候选代码已保存在 `experiment/rdp-snapshot-20261115`，提交 `1f78d2c6`。这是隔离实验，不是已经上线的优化。实验基于生产源码 `fc7ceabc`，未修改 WASM。默认仍为单区域，`sessionStorage['uniterm.rdp.snapshotRegions']='4'` 才启用候选预算；诊断也需单独启用。

## 真实连接对照

路径为飞牛 NAS Chromium → 隔离 uniTerm 服务 → Win11。实际桌面 1920×1080，浏览器为软件 Canvas2D；这不代表用户硬件加速浏览器的性能。两种设置使用完全相同的 binary、Worker 和 uniterm.16 WASM，诊断设置相同，无并行构建、测试或 CPU profiler。

源页面只让两个相距较远的 320×180 区域持续变化，中心和状态栏保持静止。先执行 A-B-B-A 四轮，每轮 30 秒；A 为区域预算 1，B 为 4。

共 3,946 批全部具有完整生命周期，始终最多一批在途，没有 trace 溢出、页面异常或过期截图提交。所有指标从原始事件重新计算并与采样文件逐项一致。

候选提交速率只变化 +0.137%，截图面积反而变化 +0.433%，都不构成可采纳收益。虽然候选组快照调用均值约低 6%，实际多区域分支没有触发，不能将这项波动归功于该优化。两组每批都仍复制约 80% 的屏幕。显示批次不是物理显示 FPS，也不保证每批对应不同的源视频帧。

由于最有利的稀疏更新场景仍未触发该分支，没有再扩大到滚动/视频的候选 ABBA。另有独立的无 profiler 滚动基线：15 秒、472 批、31.31 批/秒，间隔 P95 61.65 ms、最大 81.47 ms，超过 100 ms 为 0。

## 正确性验证

- 11 套 RDP 测试、82 项全部通过；目标 TypeScript 检查和 `git diff --check` 通过。
- NAS 真实浏览器回放比较 51 批、626,688 个像素，全部一致。截图调用后立即同步及微任务修改源画布，已捕获像素仍正确。
- 修复候选中的画布重设边界：监听该 OffscreenCanvas 实例的真实 width/height setter，包括同尺寸赋值和 A→B→A。旧截图失效，等下一次真正写入像素后全屏刷新，不提前发送清空后的画布。
- 三种原生 reset 回放均无旧像素残留。绘制或批次校验失败时释放 bitmap、停止 renderer 并走既有回退，不发送成功 ACK。
- GPU 保持一次完整输出 bitmap 的已有路径；多区域仅针对 CPU Canvas2D。

这些正确性结果只证明候选实现可继续研究，不证明它能改善本次真实工作负载。reset 修复也尚未进入生产。

## Worker 单独采样

时间线和 CPU profiler 分开采集，均使用预算 1，不能把两次执行合并解释为一次停顿。

- 时间线采样 15 秒、438 批，最大显示间隔 98.59 ms；没有重现此前 133 ms 的 ACK 延迟。此次最大本地 ACK 回调延迟 27.325 ms，与同一个 Worker 中约 26.37 ms 的 WASM 回调外壳同步调用重叠，该窗口未发现 Worker GC。它证明了回调在等待同步任务，不能仅凭墙钟时间认定全程 CPU 工作，也不能据此定位某个 Rust 函数。
- CPU-only 采样 15 秒、449 批，最大显示间隔 88.77 ms。在有效约 15.302 秒的 V8 样本权重中，`to_rgba` 占 24.66%，`createImageBitmap` 占 12.85%，WASM→JS `Uint8Array` 复制占 10.88%。这些是采样权重，不是精确 CPU 计时；也不能与以前不同版本/负载的百分比直接相减。
- 时间线中快照平均 4.614 ms，其中 `createImageBitmap` 同步调用约 4.536 ms，Promise 等待约 0.046 ms。此处主要成本发生于同步调用，`await` 不会自动将其移到别的线程。

新增可行动发现：`ironrdp-web/src/gpu.rs` 的 `call!` 会先构造参数、复制 RGBA，再由 `command()` 检查 GPU bridge 是否存在。WebGraphicsHandler 在 Canvas2D 模式也被调用，因此缺少 bridge 时这次复制可被丢弃。独立的下一候选将仅延迟参数构造，继续保留已注册但尚未 active 的 GPU 初始化命令，并用真实 WASM 红绿测试验证；不能使用一个全局 active guard 阻断 reset/create。

以上采样都未复现原来的较长单次停顿，不能声称该问题已经消失。

截图中还存在原有系统监控悬浮窗和任务栏，未操作这些程序；暂停仅指测试源的视频/滚动，不代表整个 Windows 桌面完全静止。测量结束后的只读检查发现 Win11 约 31.7 GiB 物理内存中仅约 1.3 GiB 可用，提交量约为限制的 97.2%，但五次内存采样的分页读入/写出均为 0。NAS 同期约有 8.8 GiB 可用内存，10/60/300 秒内存压力均值均为 0。它们是测量后状态，不能用于证明此前某次停顿由内存造成。

## 更靠前的区域合并

当前定制 IronRDP fork 的 session 层保留了精确区域，但 Web Canvas2D 仍使用 `GraphicsUpdate` 的包围矩形。同一已完成 GFX 帧中的分离区域可能在进入 JS 前就已合并；JS 无法拆回这些边界。

源码审查给出一条可解释本次现象的路径，并不能单独证明所有实测大区域都形成于此，Windows 编码器也可能更早产生大区域。下一轮应记录 compositor 精确区域、session 包围框、Canvas put、JS snapshot 四层面积，再决定从何处减少复制。

如接入 `take_damage_regions()`，须在每次 processing 返回后立即消费，覆盖 deferred/network/pointer input；不能等到 RAF。当前 deferred 入口的清理契约与其他入口不同，必须一起验证。保留 reset 后首次整屏刷新、GPU 隔离、处理顺序和原有 RDP 协议 ACK。协议 ACK 与 JS 显示 ACK 不是同一机制。

源码身份、文件 SHA-256、行号和最小后续修改点见证据包中的 `uniterm-snapshot-analysis/upstream-damage-review.md`。结论仅针对当前定制 fork，不代表微软或原版 IronRDP 实现。
