# VNC 浏览器图片准备优化与测量（2026-11-12）

已接入浏览器原生 Uint8Array.toBase64，替代 noVNC 1.7.0 的 JavaScript Base64 循环。保留 HTMLImageElement 解码、原有渲染队列、CopyRect 顺序和帧边界，未调整图片质量。旧浏览器没有该 API 时使用原路径。支持断开、缓存标签恢复和重复安装；没有额外 Blob URL 或画布的资源管理负担。

## 测试方法

TigerVNC 1920×1080，远端 Chrome 的本地图片画廊（96 个图片元素，重复四张照片）；浏览器 noVNC 1.7.0，固定 quality=6、compression=2，关闭本轮测试的自适应画质。每轮六次上下切换，每次间隔 2.5 秒。局域网与 20 Mbps 出站限速，另测客户端 Chromium DevTools 4 倍 CPU 降速。

性能隔离测试使用本地 Python TCP/WebSocket 转发器，排除 uniTerm UI 变化；随后用正式前端与 Go server production 构建验证真实 uniTerm 链路。客户端为 Headless Chromium 145，软件图形环境。原生 API 可用；兼容说明见 [MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Uint8Array/toBase64)。

图片准备时间是 imageRect 同步调用耗时，扣除其中绘制调用，并不等于纯 JPEG 解码 CPU 时间。标记延迟是操作到屏幕八个标记都变成新颜色的时间，不代表所有照片完成最终精细补画。Canvas 调用计时不包含全部 GPU 呈现工作。采样 getImageData 会产生读回开销，CPU 降速也不等价于真实低端设备。

## 结果

| 条件 | 六次切换图片准备耗时：原版 → 原生编码 | 标记延迟中位数：原版 → 原生编码 |
|---|---:|---:|
| LAN，第 1 轮 | 281.6 → 96.4 ms（-66%） | 66.5 → 63 ms |
| LAN，第 2 轮 | 281.3 → 91.4 ms（-68%） | 70.5 → 69 ms |
| 20 Mbps | 244.2 → 88.6 ms（-64%） | 242 → 243 ms |
| CPU 4 倍降速，原型 | 1035.4 → 414.6 ms（-60%） | 195.5 → 172.5 ms |
| CPU 4 倍降速，实际源码适配器 | 1035.4 → 420.9 ms（-59%） | 195.5 → 185.5 ms |

每轮传输约 15.60–15.63 MB；固定相同编码质量，收益不来自降低画质。CPU 降速下实际适配器一轮出现一次长任务，其余上述轮次为零；样本量不足以断言整体延迟或长任务稳定改善。LAN 仅小幅变化，20 Mbps 的标记延迟无改善。20 Mbps 最后一次画布提交的中位时间仍约 1.2 秒，持续补画没有被这项优化解决。

Blob/object URL 方案也实测过，未采用：LAN 标记中位延迟 84 ms，CPU 降速时 241 ms，均差于对应原版；其异步图片就绪等待抵消了省去字符串转换的潜在收益。

## 绘制与后续判断

源码已使用后台画布、脏区域与更新边界提交。原版 LAN 的可见 Canvas 调用累计约 276 ms / 498 次，即平均约 0.55 ms，并未证明 Canvas 提交是主要瓶颈。新编码仍存在解码队列等待，等待时间包含浏览器调度，不能与网络等待和同步 CPU 时间直接相加。

本次没有引入 WebGL2、WASM 或新的合帧机制。将 flip 简单延后到 requestAnimationFrame，再读正在被下一帧修改的后台画布，可能展示不完整更新；增加完成帧的中间画布则有额外拷贝成本。当前证据不足以支持这类改造。尚未实测 WebGL2，不能据此判定它在高分辨率、硬件 GPU 或其他客户端上无收益。

这项改动减少浏览器主线程工作，但无法承诺把 VNC 变成视频串流般流畅。后续应针对用户实际 VNC server 的编码、补画策略和带宽继续定位，不能只凭更换绘制 API 推断收益。
