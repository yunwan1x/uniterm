# RDP 图片页刷屏修复：真实连接验证

日期：2026-11-12。

## 结论

已在本次真实 Linux RDP 图片页测试中消除旧版的逐条带扫屏。最终 Docker 镜像在 20 Mbps、10 Mbps 上限的链路中，6 次大幅跳页均一次提交完整变化区域。仍存在整帧等待；不能把该结果称为 60fps、零延迟或已验证 Windows。

## 实际改动

- 新增“画面模式”：兼容 / 流畅（实验），连接编辑、普通状态栏、全屏工具栏均可选择。现有连接默认兼容，选流畅后重连并保存设置。
- 网页 WASM 接入 IronRDP 已有 GFX 动态通道，与 Display Control 共用 DRDYNVC。
- GFX 请求 32 位色；16 位色会导致测试服务端拒绝 GFX。兼容模式保留原来的 16 位设置。
- 复用已有 GFX 图面、缓存、滚动及 EndFrame 合成逻辑，完成逻辑帧后才交给 RAF 显示。
- 处理不经过 DeactivateAll 的 ResetGraphics 尺寸变化，丢弃旧尺寸脏矩形并重设画布。
- 此版本未实现 H.264/WebCodecs/WebGL2。本次实际协商 GFX RemoteFX Progressive；无 AVC 解码器时不声明 AVC 支持。

## 公平对照

旧客户端 v1.1 与最终新镜像均连接同一台 xrdp 0.10.6.1 / xorgxrdp 0.10.4，使用同一 XFCE 桌面、同一个远端 Chromium 和同一图片页。固定 1920×1080，网页显示比例为适应窗口。客户端 Chromium 使用软件图形环境。

图片页包含 96 张卡片，复用四张本地摄影壁纸并按行轮换排列。图片预先解码；每 2.5 秒在 scrollY=0 和 900 之间切换，共 6 次。只对测试连接的服务端到客户端方向限速，20/10 Mbps 是转发器上限，实际有效吞吐受调度开销影响。

| 指标 | 旧 v1.1，20 Mbps | 最终新镜像，20 Mbps | 最终新镜像，10 Mbps |
|---|---:|---:|---:|
| 6 次跳页接收数据 | 12.84 MB | 2.75 MB | 2.74 MB |
| 绘制提交总数 | 396 | 6 | 6 |
| 跳页到最终提交中位耗时 | 1124 ms | 360 ms | 535 ms |
| 单次 Canvas 同步提交最大耗时 | 0.2 ms | 1.1 ms | 1.1 ms |
| 最大浏览器 longtask | 未记录到 >50ms | 59 ms | 81 ms |

20 Mbps 下接收数据减少约 79%，完成一次更新的等待减少约 68%。这些结果来自有损图形编码和按帧合成，不能理解为同画质的无损压缩收益。大幅跳页的帧延迟不等于连续滚动 FPS。

## 录像和原始数据

- `rdp-before-after-20mbps.mp4`：左为旧 v1.1，右为最终新镜像。同限速条件、同脚本分别采集后并排显示，保持真实播放速度，没有加速。两边按录制起点对齐，输入发生时间有自动化调度误差，不能用它精确计时。
- `old20.mp4` / `final20.mp4`：独立原始视角。鼠标滚轮从网页经 RDP 输入路径送到远端，已断言远端页面实际滚动。使用每次 120 的轮动量，避免大轮动量的兼容问题。
- `old20-raw.json` / `final20-raw.json` / `final10-raw.json` / `summary.json`：独立计时轮次的数据，不包含录屏开销。
- 延迟由同一宿主机时钟计算：远端页面执行滚动时的 Date.now()，到客户端 performance.timeOrigin + putImageData 开始时刻；不含用户到服务端输入传输时间，也不测 GPU 最终显示完成时间。

## 验证

- 网页引擎原生测试：29 通过；29 项浏览器专用剪贴板测试按既有方案在原生环境跳过。
- GFX 协议/合成测试：68 通过。
- 相关前端测试：51 通过；完整前端与 Docker 构建通过。
- 最终镜像实际 UI：兼容→流畅往返切换、1280×720↔1920×1080、全屏控件、重新加载后设置保留均通过，无 pageerror。
- 旧 xrdp 0.9.12 回退连接通过：1920×1080 画布正常绘制，无 pageerror（独立桌面账号）。结果见 legacy-fallback.json。

## 适用范围和剩余问题

本轮没有 Windows 服务器凭据，所以没有验证用户那台 Windows 的编码协商。低带宽仍有整帧等待，RFX 解码仍在浏览器主线程，已观测到 59–81ms longtask。H.264/WebCodecs 是后续进一步降低带宽和解码占用的方向，本次未实现。
